# MehndiVerse — Migration Guidelines

Status: Draft (Phase 2)
Last updated: 2026-07-14

MehndiVerse uses Alembic (`apps/api/migrations/`) against PostgreSQL. This document is the process for writing, reviewing, and running migrations — schema conventions themselves are in [database-schema.md](database-schema.md).

## 1. Local setup

Migrations run against whatever `DATABASE_URL` is configured (see `apps/api/.env.example`); `migrations/env.py` reads it from the application's own `Settings` rather than a static value in `alembic.ini`, so the same migrations work locally, in CI, and in any future environment without editing `alembic.ini`.

```bash
cd apps/api
# with Postgres/Redis up via docker compose (see root README.md)
.venv/Scripts/python -m alembic upgrade head      # apply all migrations
.venv/Scripts/python -m alembic downgrade -1       # roll back the last one
.venv/Scripts/python -m alembic current            # show the applied revision
.venv/Scripts/python -m alembic history             # list all revisions
```

## 2. Creating a migration

**Schema changes** (adding/altering tables, columns, constraints, indexes): change the SQLAlchemy models in `app/db/models/`, register new modules in `app/db/models/__init__.py`, then autogenerate a draft:

```bash
.venv/Scripts/python -m alembic revision --autogenerate -m "short description"
```

**Always hand-review the generated file.** Autogenerate reliably detects added/removed tables, columns, and most constraints, but it does **not** reliably detect: constraint behavior changes that don't alter the constraint's name (e.g. tightening a `CHECK` expression under the same name), data migrations, or changes to a `CheckConstraint`'s SQL text that autogenerate's diffing considers unchanged. When in doubt, read the generated `upgrade()`/`downgrade()` against what you actually intended.

**Data changes** (seeding rows, backfilling a new column, correcting bad data): create an **empty** revision by hand and write the data operations yourself — never mix a schema change and a data change in the same migration:

```bash
.venv/Scripts/python -m alembic revision -m "seed basic categories"
```

Why separate: a schema migration should be safe to run blind in any environment (including an empty dev DB with no rows yet); a data migration often depends on the environment (you may not want to re-seed categories in a database that already has customized ones) and should be reviewable as "what data is this changing" without the schema diff noise, and vice versa.

## 3. Every migration must implement `downgrade()`

Never leave `downgrade()` as `pass` or omit it. If a migration is genuinely irreversible (e.g. a destructive data transformation with no way back), `downgrade()` should raise `NotImplementedError` with an explanation — silently doing nothing on a rollback attempt is worse than an explicit failure, because it leaves the database in a state the migration history claims isn't there.

Before merging any migration:

```bash
.venv/Scripts/python -m alembic upgrade head
.venv/Scripts/python -m alembic downgrade -1
.venv/Scripts/python -m alembic upgrade head
```

This round-trip is required, not optional — it is how Phase 2 was verified (see the Phase 2 report) and how every future migration should be verified before it's considered done.

## 4. Naming and constraints

All constraints (primary key, foreign key, unique, check, index) get an explicit, deterministic name from the naming convention in `app/db/base.py::NAMING_CONVENTION` — never let SQLAlchemy/Postgres pick an autogenerated name. This matters for two reasons: Alembic's autogenerate diffs constraints by name (an unnamed constraint looks "added + removed" on every autogenerate run instead of "unchanged"), and a migration's `downgrade()` frequently needs to reference a constraint by name to drop it.

## 5. Constraint changes (e.g. editing a CHECK's allowed values)

Because enums are `CHECK` constraints, not native types (see [database-schema.md](database-schema.md#4-enum-strategy)), adding/removing an allowed value is a normal migration:

```python
def upgrade() -> None:
    op.drop_constraint(op.f("ck_bookings_status_valid"), "bookings", type_="check")
    op.create_check_constraint(
        op.f("ck_bookings_status_valid"), "bookings", "status IN (...)"
    )

def downgrade() -> None:
    op.drop_constraint(op.f("ck_bookings_status_valid"), "bookings", type_="check")
    op.create_check_constraint(
        op.f("ck_bookings_status_valid"), "bookings", "status IN (...)"  # previous list
    )
```

**Always wrap the constraint name in `op.f(...)`.** Because `env.py` registers a naming convention on `target_metadata`, Alembic treats a bare string passed to `op.drop_constraint()`/`create_check_constraint()` as an unrendered convention token and re-applies the convention to it — producing a doubled name like `ck_bookings_ck_bookings_status_valid` and failing with "constraint does not exist". `op.f()` marks the string as already-final so it's used verbatim.

Update the corresponding `StrEnum` in `app/db/enums.py` in the **same** migration/commit as the constraint change — they must never drift.

## 6. What never gets a migration that removes it

Per [database-schema.md](database-schema.md#6-foreign-keys-and-cascade-policy), never write a migration that drops or truncates `payments`, `refunds`, `payouts`, `booking_status_history`, `audit_logs`, or any other financial/audit table's data as part of a routine change. If a genuine, deliberate data-retention decision requires removing old audit data, that is a separate, explicitly-reviewed migration with sign-off noted in the PR description — not something bundled into an unrelated schema change.

## 7. Testing migrations

Database model tests (`apps/api/tests/db/`) run against a real Postgres (see the backend CI job and root `docker-compose.yml`), not SQLite — this schema relies on Postgres-specific behavior (native `UUID`, `JSONB`, functional indexes, `ON DELETE RESTRICT`/`SET NULL` semantics) that SQLite cannot faithfully emulate. The test fixtures apply `alembic upgrade head` against a disposable test database before running, mirroring what CI and local development both do.
